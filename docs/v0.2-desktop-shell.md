# BEKAL V0.2 — Desktop Shell

## Objective

Turn the existing BEKAL React interface into a first-class Windows desktop experience without rewriting the proven V0.1 receipt-processing core.

The approved desktop direction is **Tauri 2**.

## User experience target

The user should be able to launch BEKAL as a normal Windows application with its own window, taskbar entry, and later installer, rather than manually opening a browser tab.

The desktop shell may continue to use loopback-only local services internally. The user-facing goal is a standalone desktop experience, not a full rewrite of FastAPI/PostgreSQL/OCR.

## Preserved V0.1 architecture

- React + TypeScript frontend remains the UI.
- FastAPI remains the backend API.
- PostgreSQL remains the persistent database.
- Local Tesseract OCR remains the scanned-PDF fallback.
- Docker Compose remains the initial service runtime for backend/PostgreSQL during this milestone.
- Existing receipt-processing semantics, privacy rules, and V0.1 data remain unchanged.

## Phase 1 — Tauri desktop shell

Deliver a Tauri 2 Windows shell around the existing frontend.

Acceptance criteria:

1. `npm run tauri dev` opens a BEKAL desktop window.
2. The window uses the existing React UI, not a duplicate UI.
3. Browser-only V0.1 remains usable.
4. Frontend API access works in both browser mode and Tauri mode through one small API URL abstraction.
5. Backend/PostgreSQL remain loopback-only.
6. Existing V0.1 tests and frontend build continue to pass.
7. `cargo check` / Tauri development build succeeds on Windows.
8. No real receipts, runtime data, credentials, or generated installer artifacts are committed.

## Phase 2 — One-click lifecycle

After Phase 1 is stable, make the desktop app manage the local BEKAL service lifecycle so the owner no longer needs separate Start/Open/Stop shortcuts for normal use.

Target behavior:

```text
BEKAL.exe
  -> verify local prerequisites/services
  -> start BEKAL backend/database if required
  -> wait for health
  -> open BEKAL desktop window
  -> stop only BEKAL-owned transient services on clean exit where safe
```

Docker Desktop may remain a prerequisite for this phase. Removing Docker is a separate future architecture decision.

## Phase 3 — Windows packaging

After lifecycle management is reliable:

- create branded Windows executable/installer,
- add BEKAL icon and metadata,
- document installation and upgrade behavior,
- verify that application updates do not destroy local receipt/database data.

## Non-Goals

This milestone does **not** include:

- replacing FastAPI,
- replacing PostgreSQL,
- removing Docker,
- rewriting OCR,
- mobile applications,
- authentication,
- cloud hosting,
- HANA integration,
- new grocery/recipe/pantry features,
- changing V0.1 receipt semantics.

## Safety principle

Desktop packaging must not weaken the V0.1 privacy boundary. Backend and database ports stay bound to loopback only, and real receipt/runtime data stays outside Git.
