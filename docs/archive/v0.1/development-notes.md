# Development notes

From the repository root, run `docker compose up --build -d`. Use `docker compose ps` to confirm all three services report healthy. Run `docker compose exec backend alembic upgrade head` to apply the foundation migration.

The frontend is available at `http://localhost:5173`, the API at `http://localhost:8000/api/health`, and the database check at `http://localhost:8000/api/health/db`.

To exercise Phase 3, choose a PDF in the frontend and click **Validate and preview**. The backend returns a temporary UUID and an original-PDF preview URL, then automatically extracts and prepares review data. The page shows whether embedded text or local OCR was used. Compare the PDF with the form, edit metadata, use the pen button to edit a row, and add/delete rows. Total and field warnings update as you correct the candidate. For an unreadable PDF, use the manual-entry form beside the PDF. Click **Discard preview** to remove the candidate early. Candidates also expire after one hour and are cleared when the backend restarts. Review edits are in browser memory only and are lost on refresh or re-extraction unless explicitly confirmed and saved.

For Phase 4, apply migrations with `docker compose exec backend alembic upgrade head`. After reviewing a candidate, check the acknowledgement and select **Confirm & Save**. If a possible duplicate warning appears, compare the original and choose whether to **Save anyway**. Successful saves show the receipt ID, store, date, item count, and total. The permanent PDF is under ignored `runtime-data/receipts/`; the database stores its relative path. The temporary candidate is deleted after success. To verify local data, use `docker compose exec postgres psql -U bekal -d bekal -c "SELECT id, original_file_path FROM receipts"`, adapting the database name if configured differently. Use synthetic PDFs for tests.

For Phase 5, open **Receipt History** from the header. The table lists saved date, store, item count, and total. **View** opens the structured record beside its original PDF. **Edit** opens the same record with editable metadata and pen controls for item rows. Row saves only change the on-screen form; **Save changes** is required to update PostgreSQL. The original PDF is never replaced during an edit. **Delete** requires a second explicit confirmation and removes the receipt, its item rows, and its private PDF. If a PDF is already missing, the record can still be removed. The API uses `GET /api/receipts`, `GET /api/receipts/{id}`, `GET /api/receipts/{id}/pdf`, `PUT /api/receipts/{id}`, and `DELETE /api/receipts/{id}`. The PDF endpoint resolves the database record's relative path under the configured private root; runtime storage is never served as a static directory.

File and database operations cannot be fully atomic. During deletion, BEKAL temporarily renames the PDF, commits the database removal, then unlinks the renamed file; ordinary database failures restore the PDF. On backend startup after migrations, private-file reconciliation restores a staged PDF if its database receipt remains, or finishes deleting it if the database receipt is gone. A PDF left without a database receipt after an interrupted save is moved into private `runtime-data/receipts/.recovery/` rather than discarded. Inspect and handle quarantined files privately; they are never served by the API. Restart the backend after first applying migrations if it started before the receipt tables existed. Older staged deletion files created before Phase 8 did not encode the receipt ID and cannot be matched automatically; inspect them manually if a receipt PDF is missing. Do not expose the private storage directory publicly.

For Phase 6, select **Dashboard** and choose a calendar month. The frontend defaults to the browser's current month; the read-only API is `GET /api/dashboard?month=YYYY-MM`. Only permanently saved MYR receipts with a receipt date in the selected month count. The spending total sums known receipt final totals and explicitly reports receipts with missing totals. Top categories sum known item line totals, so their amounts can differ from receipt totals. Most-purchased products count saved item rows rather than inferred quantities. Comparable price history requires the same canonical product and unit on at least two receipts, a known unit price, positive quantity, and a row checked against the PDF; ambiguous repeated product/unit prices on one receipt are excluded. Recent receipts link to the existing saved-receipt view. Edits and deletions appear on a fresh dashboard load or by selecting **Refresh**. Empty and partial months do not invent values.

For Phase 7, open **Receipt History** and download `receipts.csv` or `items.csv`. The endpoints are `GET /api/exports/receipts.csv` and `GET /api/exports/items.csv`. They export all permanently saved MYR receipts and their item rows at request time, including saved edits; deleted records disappear. Empty databases return headers only. Files use UTF-8 with a byte-order mark for Excel, ISO dates, decimal MYR amounts without currency symbols, blank cells for unknown values, and a leading apostrophe on potentially executable spreadsheet text. CSVs are generated in memory and are not retained by the backend. Treat downloaded files as private data and keep them outside the repository.

For host-based development, install frontend dependencies with `npm install` in `frontend/`, and install the backend with `python -m pip install -e '.[dev]'` in `backend/`. Install Tesseract and make its executable available on `PATH` for scanned-PDF OCR; Docker includes it already. Set `DATABASE_URL` to a local PostgreSQL URL before running the database check or migrations. Run `npm run dev`, `uvicorn app.main:app --reload`, `npm run build`, and `python -m pytest` from their respective directories.
